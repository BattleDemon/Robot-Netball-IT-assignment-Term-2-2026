So what movement.py actually does. It is a shared navigation module that both the Attack and Defence robot can import. 
The main thing is the Driver class which handles all the wheel odometry, field mapping, boundary checks, foul detection 
via the colour sensor, and the pivot movement which is important for netball rules. I made it so you just change the 
TEAM variable at the top from "ATTACK" to "DEFENCE" and it automatically sets the correct start position and which hoop 
you are aiming at. For Attack the start position is near the far end of the field at (79, 199) roughly, and the hoop it 
shoots toward is at (79, 0). For Defence it starts near (79, 20) and shoots toward (79, 219). This means no confusion during 
testing about which side is which. Even though Tim has given us a yellow circle to work with, it is just another coordinate 
that would be roughly (79, 109.5). The only time the yellow circle matters in the rules is for the restart after a goal but that
should be a human placing the robot there manually. It doesn't need to autonomously find the yellow circle with a sensor.

The way the odometry works is there is a background thread running at 20 Hz that reads the motor encoder angles every 0.05 seconds 
and calculates how far each wheel has turned. From that it works out the average distance travelled and the change in heading, 
then updates the x and y position using trig. The heading convention I used is 0 degrees = facing toward the attack hoop 
(positive y direction), 90 degrees = facing right (positive x), etc. This made the most sense because the field is longer than 
it is wide so having 0 point down the length felt natural.

I also added a MyTank class at the bottom which is just a thin wrapper around Driver so that Hugo's old code from DefenceMain.py 
that imports MyTank does not break. Dexter's code imports Driver directly so that works too.

For foul detection there is a is_in_foul_area() method that first checks the colour sensor for white, and if the sensor glitches it 
falls back to checking the theoretical position against known foul zone coordinates. There is also sees_black_tape() for boundary 
detection and is_in_bounds() with a 5cm margin so the robot knows if it is getting too close to the edge.

The pivot method is important because of the netball rule where while holding the ball one wheel must remain still. 
So pivot("LEFT", speed, seconds) locks the left wheel and moves the right one, and vice versa. This means Zen can call that when the 
attack robot has the ball and needs to pivot before shooting.

There are also some helper methods like face_hoop() which turns the robot to face the target hoop, angle_to_hoop() which calculates 
what heading the robot needs, distance_to_hoop() for shot power calculations, and drive_to_point(tx, ty) which turns toward a coordinate 
and drives straight there. These will be useful for Zen's movement code and also for the turret/shooting code since I can use 
distance_to_hoop() to figure out how hard to shoot.

One thing I need to test and probably tweak is the WHEEL_DIAMETER and TRACK_WIDTH constants. I put 5.6cm for the wheel diameter and 12.3cm 
for the track width but these need to be measured on the actual robot because if they are wrong the odometry will drift. 
Also the foul zone coordinates are approximate and need to be checked against the actual field.

If we plug a gyro sensor in later there is support for that too. The odometry loop will blend gyro readings with encoder readings 
(90% encoder, 10% gyro) to help fight drift. We do not have a gyro allocated yet but the code is ready for it if we do lol.

Links I used / that helped:

- IR Seeker v2 docs: https://irseeker.buildingblockrobotics.com (Dexter found this, we use it for the IR thread)
- General differential drive kinematics: https://www.cs.columbia.edu/~allen/F15/NOTES/icckinematics.pdf (I used this for the math behind arc length per wheel during turns,
 specifically the formula wheel_dist = (angle/360) * pi * track_width)

I think the odometry math itself is standard differential-drive kinematics... encoder deltas give distance per wheel, average of both wheels gives forward distance, 
difference divided by track width gives heading change.
